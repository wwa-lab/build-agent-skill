# CodeCup 2026 提交材料：Atlas Engineering Delivery Hub – Build

本页是[Situation → Solution → Result 主线](atlas-engineering-delivery-hub-build-pitch.md)的提交摘要。案例证据与测量口径在主线及案例库维护。

## 项目与价值

**Atlas Engineering Delivery Hub – Build** 面向 IBM i 开发者、评审者及交付团队，将业务需求与旧代码知识转成有依据、符合维护约定、能够逐项评审的实现工作。

项目形态是可复用的领域 Skills 工具包，位于整体 Atlas 的 M4 Build 阶段。期望改善人工投入、返工和交接质量，当前以已有工作流和合成 POC 的静态证据说明进展。

## 1. Situation — 为什么要做？

IBM i 改动需要同时理解现有逻辑、文件布局、调用契约和团队维护惯例。[Pilot 复盘](../article-pilot-retrospective.md)记录了直接的使用反馈：小改动被完整规格链拖重；fixed-format 生成代码缺少习惯的分隔、注释与命名；旧代码理解和测试准备没有接入。

这些问题让开发与评审继续承担上下文补齐和产物整理工作。Pilot 是定性反馈，尚无工时基线；我们不据此推算整个团队的成本。

## 2. Solution — 如何解决，有什么特点？

| 设计 | 对应问题 | 价值逻辑 |
| --- | --- | --- |
| 满足条件的小改动走 Mini Requirement → Program Spec 短路径 | 已知内容重复经过全部文档层 | 根据任务保留必要步骤，减少重复准备的机会 |
| 旧源码、分层规格、文件／参数契约和维护风格共同指导生成 | 模型输出缺少既有系统与团队上下文 | 让领域经验成为可以复用和评审的依据 |
| BR 追踪、跨规格引用、评审规则与静态检查随产物交付 | 评审需要重新寻找规则与实现关系 | 提供可逐项核对的实现线索和问题处理记录 |

特点在于这三项机制针对 IBM i 日常交付的组合。SDD 和 Skills 是采用的方法；当前不主张这些方法是本项目首创，也没有竞品对照结果。

16 个 Skills 覆盖分析、规格、程序／DDS 生成、评审、测试准备与编排协议。技能目录是实现说明，路演先讲问题和解决机制。

## 3. Result — 已有结果与收益

[多仓订单履约与结算合成 POC](cases/rpgle-flow-poc/README.md)保留了完整需求、设计、8 份程序规格、24 份文件规格和 35 个源码文件。32 条业务规则可关联到规格步骤与源码，94 个步骤有静态定位；审阅记录包含消息覆盖、重复声明、回滚结果和去重查询等问题的修正。

这些结果说明，工作流已用于一个有跨程序、跨文件依赖的案例，形成可阅读、可追踪、可本地复核的实现材料。现有检查不证明业务正确性，也不代表每个问题都由自动工具发现。

| 结果层级 | 当前状态 |
| --- | --- |
| 工作流、领域规则、规格及源码案例 | 已有 |
| 静态追踪、契约检查与修正记录 | 已有，局限随报告说明 |
| 人工投入、返工和交接质量收益 | 待真实案例对比测量 |
| IBM i 编译、业务执行、模型评测结果 | 当前 POC 尚无 |

下一步选择验收明确的脱敏真实增强案例，记录总人工投入、返工分类、修正轮次和独立评审质量，再补充编译与回归证据。[测量方法](atlas-engineering-delivery-hub-build-pitch.md#希望带来的收益与下一步测量)将基线、生成后的人工修正和验收条件纳入比较。

4. Result：展示能核对的证据，再说明待测收益与真实案例计划。
